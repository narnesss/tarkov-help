# Источники данных, схема и публикация контента

Статус на 2026-10-17: описание текущей архитектуры и обязательный контракт дальнейших изменений.
Разделы «Требуется» задают приёмку, а не утверждают, что механизм уже реализован.

## Источники истины

- Схема — последовательность [миграций](../database/migrations/) и выбранный ими DDL
  [MariaDB](../database/migrations/sql/2026_10_15_domain.mysql.sql). Сверять с migrations действующей БД.
  [Карта БД](../docs/architecture/database-map.md) — навигация, старые планы — история, не полная схема.
- SQL: users/sessions/user_state/rate_limits; player_profiles, player_identities, player_oauth_states,
  player_auth_locks, player_emails, player_email_challenges, player_password_resets,
  player_password_history, player_legal_consents; редакторы/роли/сессии Orchid.
  Пользовательский прогресс user_state.value — сериализованное состояние в SQL, не файловый контент.
- SQL: идентификаторы, режимы, published/archived, версии и типизированные связи предметного домена.
  Точный перечень редактируемых wiki_* сущностей — [WikiSchema::TYPES](../app/Services/WikiSchema.php);
  служебные wiki_sources/wiki_projection_states/wiki_import_issues и блокировки — миграции.
- Файлы CONTENT_DIRECTORY: только неизменяемые документы, на которые ссылаются
  quests.payload и content_datasets.payload как @file:SHA256. SQL выбирает действующую версию;
  сам gzip без SQL-ссылки не становится опубликованным. Native JSON-колонки контента не добавлять.
- public/data — исходный seed/совместимый статический набор; dist/HTML, поисковые индексы,
  content_references, пересоздаваемые проекции и кэш — производные, не копия рабочих правок.
  public/assets — статические медиа. Приватные SQL/content в dist не копировать.

Приоритет по полям: типизированные поля и связи из DDL принадлежат SQL; их вхождения
в совместимом JSON — представление. Немоделируемые описания/диалоги/медиа и дополнительные
поля принадлежат документу, выбранному SQL-ссылкой, не seed. Логическая сущность не имеет
двух независимых владельцев: текстовый редактор передаёт команду синхронизации, а не
создаёт право редактировать JSON вне сервиса. При расхождении остановить публикацию
и сверить revision/wiki_sources; не выбирать более новый файл по mtime автоматически.

## Точный объём файлового исключения

quests.payload содержит совместимый документ квеста: описание/диалоги/прохождение,
медиа и атрибуцию, дополнительные поля целей/условий/наград и старую API-структуру.
ID, состояние публикации и моделируемые связи не переносятся из SQL в самостоятельный файл.

content_datasets.payload содержит публичные справочники следующих семейств:
- home.json; docs.json, maps.json, spawns.json, source.json;
- guide/items-{pve,regular}.json, guide/quests-{pve,regular}.json,
  guide/reference-{pve,regular}.json: предметы/квесты и вложенные справочники навыков,
  убежища, достижений, крафтов, торговли и характеристик предметов;
- guide/bosses.json, guide/btr.json, guide/gunsmith.json, guide/story.json, guide/wiki-quests.json;
- guide/quest-{choices,conditions,content,map-index,media,reward-support}.json,
  guide/ticket-map.json, guide/objective-patches.json, guide/quest-patch-1150.json,
  guide/catalog-update.json, guide/media-{audit,localization}.json, guide/provenance.json;
- raid/maps.json, raid/item-names.json, raid/loose-items.json, raid/quest-index.json,
  raid/{source,correction-provenance,document-calibration,navigator-provenance}.json;
- raid/{карта}.json и raid/pve/{карта}.json: карта из списка customs, factory,
  ground-zero, icebreaker, interchange, lighthouse, reserve, shoreline, streets-of-tarkov,
  terminal, the-lab, the-labyrinth, woods.

Это перечень допустимого назначения, не разрешение импортировать отсутствующие файлы.
Фактические пути сверять с content_datasets, seed и [DatasetCatalog](../app/Services/DatasetCatalog.php).
Новое семейство требует дополнения перечня. Аккаунты, пароли, контакты, согласия, токены,
сессии, прогресс и журнал администрирования в файловое исключение не входят.

## Направление изменений и восстановления

Предметный редактор: валидация/CAS → SQL wiki_* → WikiPublisher обновляет документ,
сохраняя немоделируемые поля → новые SQL-ссылки. Текстовый редактор/пакет контента:
документ → QuestEditor/ContentDataset → WikiSync/WikiImporter обновляют типизированную проекцию.
wiki_sources фиксирует соответствие. Обе ветки должны проходить через общую сериализацию
и транзакцию, а не независимо исправлять две копии одного поля.
Не запускать полный seed поверх редакторских изменений; одноразовые пакеты версионировать.
Восстановление: согласованные SQL + необходимые версии content → проверка ссылок/FK →
проверка проекций/индексов и пересоздание кэша; никогда не восстанавливать SQL из dist.

## Порядок публикации и обрыв процесса

1. Проверить права, входные данные, revision; получить блокировку редактирования.
2. Сериализовать документ, вычислить SHA-256, записать gzip в приватный временный файл
   на той же файловой системе; проверить полную запись, распаковку и hash до публикации.
3. Атомарно переименовать файл в конечный путь. Для гарантии при отключении питания
   дополнительно обеспечить fsync файла/каталога или документировать ограничения хранилища.
4. В SQL-транзакции сохранить доменные изменения, ссылки и маркеры проекции; commit.
5. Только после commit объявить новую revision и инвалидировать/обновить кэш.
   Для надёжной доставки побочных действий предусмотреть транзакционный outbox.
   Потеря уведомления не должна скрывать новую версию: revision проверяется по SQL.

Уже есть: [ContentFiles](../app/Services/ContentFiles.php) использует hash, временный файл,
rename и проверку gzip/hash при чтении; QuestEditor и WikiSync используют транзакции/CAS.
На 2026-10-18 ContentFiles дополнительно сверяет количество записанных байтов, распаковывает
временный файл и проверяет SHA-256 до rename/возврата ссылки. Изолированные тесты моделируют
короткую запись, повреждение и отказ rename: временный файл очищается, старая версия доступна.
Это не проверка отключения питания: fsync файла/каталога и долговечность хранилища не гарантируются.
Порядок after-commit/кэша и обрывы SQL-публикации требуют отдельной проверки; saved-hook
сам по себе не доказывает after-commit.

Crash-тесты: обрыв во время записи/до rename/после rename/до commit/после commit до кэша.
До commit читается старая согласованная версия; после — новая; повтора пакета недостаточно
для дублирования записей. Потеря питания проверяется отдельно от исключения PHP.
Откат SQL может оставить недостижимый файл; отсутствующий/повреждённый файл не подменять seed.

Очистка content: сначала mark от всех действующих ссылок, архивов, сохраняемых манифестов
backup/restore и незавершённых публикаций; затем согласованный повторный mark и удаление
только недостижимого с запасом времени. Не удалять файлы параллельной публикации.
Автоматического безопасного GC в ContentFiles сейчас нет; не заменять его массовым rm.
Срок хранения backup и его файлов согласовывать по [контракту восстановления](recovery-contract.md).

## Обновление игровых данных и проверка публикации

Требование к каждому новому импорту: фиксировать источник/URL, время получения UTC,
PVE/PVP, версию игры/набора и hash; соответствие прежних импортов проверять отдельно.
Перед записью давать dry-run: добавленные, изменённые, исчезнувшие записи, неоднозначные
ID и конфликты редакторских правок. Исчезновение из источника — кандидат в архив/проверку,
не каскадное удаление прогресса; внешний ID сохранять, локальные ID точек разделять по карте/режиму.
Возобновление импорта и повтор одного пакета должны быть идемпотентны; не переносить PVE в PVP.

Для create/edit/unpublish квеста проверять карточку, поиск, фильтры, карту, зависимости,
награды и SEO (исходный HTML, canonical, sitemap, HTTP-статус). Повторить после обычной
перезагрузки и с прогретым кэшем, в обоих режимах; ID/личные отметки не менять.
Обязательно проверить slug, уже существующий в dist: устаревший ASSETS HTML не должен
публиковать снятый квест. Его обработку согласовать с [контрактом клиента/API](client-api-contract.md).
