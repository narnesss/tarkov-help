# Личный кабинет и способы входа

## Дополнительные сведения профиля

В кабинете редактируются имя и необязательные телефон, страна, город, пол и возраст
(целое число 1–120). Телефон нормализуется: + и 7–15 цифр. Это неподтверждённый контакт,
он не используется для входа, восстановления или автопривязки. Подтверждённая почта
показывается без редактирования. Дата регистрации — users.created_at, активность —
player_activity с точностью до минуты для успешных обращений к личному API.
До первого обращения после обновления активность неизвестна.

GET /api/auth/profile выдаёт анкету только владельцу с private, no-store. Контакты
не включены в session.profile, публичный контент, экспорт HTML, IndexedDB и localStorage.
POST сохраняет разрешённые поля; прежний запрос изменения имени не затирает анкету.
Сохранение анкеты требует profile_version из GET и отклоняет устаревшую форму с 409.
Если отдельный контакт отсутствует, почта показывается из подтверждённой identity;
это не создаёт молча контакт восстановления. passwordResetAvailable отражает наличие
именно подтверждённого контакта player_emails.
HTML, управляющие знаки, неверные типы и диапазоны, изменение почты/дат отклоняются
сервером. Браузер независимо проверяет поля и показывает ошибки рядом с ними.

Кнопка «Сбросить пароль» открывает прежнюю форму восстановления, не показывает авторизацию
вошедшему пользователю и не отправляет письмо до нажатия. Для вошедшего пользователя
сервер выбирает собственную подтверждённую почту, игнорируя подменённый адрес запроса.
После смены пароля отзываются сессии и открывается вход; ID, способы входа и прогресс прежние.
Новые поля добавляются nullable-миграцией, старые строки не переписываются.

Страница `/account` — общая Blade-оболочка, экспортируемая в Cloudflare. Персональные
данные загружаются только через существующие `/api/session` и `/api/state` с private,
no-store. В статический HTML не попадают логины, отметки и другие данные игроков.
Публичная `/privacy` описывает фактические данные входа и прогресса, cookie, локальные
копии и контакт поддержки; используется в настройках брендинга OAuth.
В текущих исходниках версии ресурсов задаются вручную. Требование автоматического
fingerprint графа CSS/JS и проверка обычной перезагрузки описаны в
[контракте клиента/API](client-api-contract.md); устаревшие номера profile-N не являются
действующим контрактом. Очистка кэша пользователем не считается способом публикации.

`account-model.mjs` рассчитывает сводку отдельно для PVE/PVP: выполненные квесты,
построенные уровни убежища и полученные достижения. Учитываются только существующие ID
актуального каталога. Дубликаты и удалённые элементы не увеличивают процент. Из кабинета
можно открыть раздел, активный квест, синхронизировать данные или перенести файл профиля.

Существующие логин/пароль, opaque cookie, HMAC CSRF и CAS прогресса сохранены.
Новый аккаунт не наследует гостевые отметки автоматически: перенос выполняется экспортом
и импортом профиля, о чём форма предупреждает до регистрации.

## Google и Discord

`POST /api/auth/oauth/{provider}/start` проверяет текущую сессию, Origin и HMAC CSRF,
создаёт случайный одноразовый state на 10 минут и возвращает URL провайдера. В БД
сохраняется только SHA-256 state и сессии. Callback возвращается на публичный Cloudflare
origin; JS удаляет code/state из адресной строки и отправляет их защищённым POST в
`/api/auth/oauth/{provider}/finish`. Worker продолжает принимать только JSON-ответы API,
не пересылает секреты и не требует разрешать редиректы PHP.

Laravel обменивает code на access token на фиксированном HTTPS endpoint, читает профиль
провайдера и сразу забывает access token. В БД остаётся provider/subject, отображаемое имя
и прежний ID игрока. Повторный вход находит тот же аккаунт и прогресс. Сессия ротируется,
прежняя отзывается. State связан с сессией и провайдером и атомарно потребляется до обмена.

Вошедший игрок может явно подключить провайдера к своему аккаунту. Новый способ входа
автоматически подключается к существующему ID при однозначном совпадении подтверждённой
почты: Discord `verified === true`, Google `email_verified === true` и Gmail либо
совпадающий Workspace `hd`. Для внешнего Google email одного email_verified недостаточно:
нужно войти в существующий аккаунт и подключить сервис. Неоднозначное совпадение,
попытка заменить уже связанный subject или второй профиль того же провайдера дают 409.
Уже известный subject всегда сохраняет прежнего владельца, даже если почта изменилась.
Решения сериализуются singleton FOR UPDATE, запись identity и выдача сессии транзакционны.
Ни неподтверждённая почта, ни похожий логин не связывают аккаунты. Телефон в выбранных
scopes отсутствует; телефонный вход требует отдельного подтверждения и здесь не добавлен.

Для входа Google используются openid/profile/email, Discord — identify/email. Расширение
Discord требует нового согласия на email. Ранее созданные аккаунты не имели email/телефона:
их владелец один раз входит по логину и подтверждает e-mail либо явно подключает провайдера. Ранее подключённые
провайдеры сохраняются; email/аватар появятся при следующем OAuth-входе.

`PlayerProfiles` обогащает profile.name/avatar/customName в ответах session/auth. Таблица
player_profiles не меняет users.username: парольный вход и ID прогресса прежние. Имя
первого провайдера и безопасный HTTPS URL его аватара закрепляются при регистрации, пользовательское имя
не перезаписывается. `POST /api/auth/profile` принимает обязательную строку display_name
1–64 символа после trim, без управляющих символов и < >, требует named account/Origin/HMAC CSRF.
Пустая строка и null отклоняются; сброс к имени внешнего провайдера не поддерживается.
Имя/аватар берутся у первого провайдера только при создании нового аккаунта;
вход, явная привязка и автопривязка второго провайдера их не меняют. Ручной аккаунт
сохраняет своё имя и инициалы. Read-fallback старых строк на provider_name в PlayerProfiles
не является разрешением записать null. Адреса
аватаров ограничены Google googleusercontent.com и конструируемым Discord CDN; произвольные
URL и серверное скачивание исключены. Контакт email выдаётся только его владельцу в
отдельном private API; токены и коды подтверждения клиенту не возвращаются.

## API подтверждения e-mail старого аккаунта

Ранее кабинет содержал форму ручного ввода e-mail; теперь она убрана. Описанные ниже
API сохраняют серверный контракт и не означают наличие этой формы в интерфейсе.
Автопривязка использует подтверждённые контакты существующего аккаунта и профиль провайдера.
`GET /api/auth/email` для авторизованного владельца показывает подтверждённую почту и активный
запрос. `POST /api/auth/email/send` принимает адрес, `POST /api/auth/email/verify` —
challenge_id и восьмизначный код из письма. Все POST требуют прежние Origin/HMAC CSRF;
гости отклоняются. Контакт сохраняется в player_emails с прежним user_id; users и user_state
не изменяются. Занятые адреса проверяются также в provider identities, при запросе и подтверждении.

Код создаётся random_int, живёт 30 минут и допускает 5 попыток; HMAC связан с ID игрока,
случайным challenge_id и адресом. Запрос нового кода отменяет старый. Повтор через 60 секунд,
лимиты: 5 писем/час на игрока, 10 на IP, 3 на адрес; ключи rate_limits не содержат контактов.
Коды не сохраняются в открытом виде, JSON, логах или очереди. Ошибка SMTP удаляет конкретный
запрос и возвращает 503, не заявляя об успешной доставке. Принятие SMTP не доказывает доставку
в inbox: финальная проверка выполняется владельцем почты по реально полученному письму.

Production использует выделенный mailer alwaysdata: smtp-narnes.alwaysdata.net:587,
обязательный STARTTLS с проверкой сертификата, timeout 5 сек. С сервера alwaysdata SMTP
не требует пароля. Адрес отправителя по умолчанию narnes@alwaysdata.net; переопределения
PLAYER_EMAIL_MAILER / PLAYER_EMAIL_FROM вне Git. Локально функция отключена без выбранного
транспорта. Log/failover/roundrobin не подходят для проверок; array разрешён только в tests.

Подтверждённая почта участвует в выборе OAuth-владельца наравне с подтверждёнными адресами
провайдеров. Gmail/Workspace и Discord с проверенной почтой автоматически подключаются
к старому ID. Для внешней почты Google по-прежнему нужна явная привязка из аккаунта:
однократное подтверждение адреса на сайте не делает Google авторитетным для его будущего владения.

## Включение на alwaysdata

Нужны OAuth-приложения владельца проекта. Секреты нельзя сгенерировать вместо Google
или Discord: их выдаёт кабинет соответствующего провайдера.

1. Google: создать OAuth Client типа Web application в Google Auth Platform.
   Authorized redirect URI: `https://tarkov-compass.narnesss.workers.dev/account?oauth=google`.
   Настроить аудиторию приложения; при режиме Testing добавить разрешённых тестовых пользователей.
2. Discord Developer Portal: создать приложение, в OAuth2 добавить redirect:
   `https://tarkov-compass.narnesss.workers.dev/account?oauth=discord`.
   Установка бота на сервер и bot token не нужны.
3. В приватном `/home/narnes/tarkov-shared/.env` задать `GOOGLE_CLIENT_ID`,
   `GOOGLE_CLIENT_SECRET`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`.
   Не менять APP_KEY, параметры БД или секрет Worker. Не добавлять секреты в Git,
   Cloudflare vars, клиентский JS и логи.
4. Обновить Laravel config cache и перезапустить PHP. `GET /api/auth/options` возвращает
   только доступность и факт подключения провайдера для текущего игрока.
5. В браузере выполнить реальный вход и повторный вход для каждого провайдера, проверить
   тот же ID игрока и сохранённый прогресс. Интерактивное согласие предоставляет владелец.

Без реквизитов кнопки видны с честным состоянием недоступности, обычный вход работает.
Для ограниченной установки используется workflow `player-oauth.yml`: prepare создаёт
RSA-ключ только на alwaysdata, apply принимает исключительно OAEP-SHA256 шифротекст.
`PlayerOAuthSettings` разрешает только полные пары CLIENT_ID/CLIENT_SECRET Google/Discord,
атомарно обновляет shared .env и сверяет неизменность всех остальных переменных.
Приватный ключ и расшифрованный временный файл удаляются после apply. Секреты не
попадают в GitHub Secrets/логи/артефакты; перед передачей шифротекста нужно разрешение владельца.
Тесты HTTP подменяют только ответы внешних провайдеров; они не заменяют финальную проверку
настоящего consent flow после настройки приложений.

Источники: [Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server),
[Discord OAuth](https://docs.discord.com/developers/topics/oauth2).

После подтверждения кнопка отправки скрыта для текущего адреса; изменение адреса снова показывает её.
Тема письма — `Tarkov Compass - Email verification code` (английский ASCII), чтобы журнал
alwaysdata отображал её без искажений. Тело остаётся русским UTF-8 текстом; код действует 30 минут.

## Восстановление пароля

На форме входа ссылка «Забыли пароль?» открывает `/account?view=reset`. Гостевая opaque-сессия
и прежний Origin/HMAC CSRF обязательны для POST `/api/auth/password/request` (email) и
`/api/auth/password/reset` (challenge_id, code, password, password_confirmation). После
успеха форма возвращается ко входу с прежним логином; новый аккаунт не создаётся.

Подходит только адрес, подтверждённый в кабинете и сохранённый в player_emails. Один адрес
провайдера без такого подтверждения не включает сброс пароля. Ответ запроса и ограничений
одинаков для известных и неизвестных адресов. Отправка отложена до завершения HTTP-ответа
через Laravel defer, без очереди; SMTP-ошибка не раскрывает существование аккаунта.
Повтор через 60 секунд, 3 запроса/час на адрес, 10 на IP. Код 8 цифр/1 час/5 попыток,
привязан к браузерной сессии, текущему контакту и снимку хеша прежнего пароля. Код, новый
пароль и адрес не передаются в URL, клиентское хранилище, логи или JSON-контент.

Сброс меняет только users.password_hash, отзывает все прежние сессии и незавершённые
OAuth/почтовые запросы владельца. ID, логин, связи Google/Discord, имя и весь PVE/PVP-прогресс
сохраняются. Повтор кода, другой браузер, смена контакта/пароля, истечение срока и перебор
отклоняются. Письмо имеет английскую тему `Tarkov Compass - Password reset code` и русский текст.

Новые пароли: минимум 12 символов (рекомендуется 16+), максимум 72 байта, заглавная/строчная
латиница, цифра, знак пунктуации/символ. Запрещены распространённые слова с простыми заменами,
логин, последовательности от 6 символов, повторы и типовые даты. Сервер проверяет регистрацию
и восстановление; история только хешей запрещает текущий и прежние пароли с момента внедрения.
Проверка уникальности относительно других сайтов и любых слов невозможна; форма рекомендует
отдельный случайный пароль. Вход со старым паролем сохраняется. Код восстановления действует
1 час; подтверждение почты остаётся 30 минут.

Сохранение имени не перезагружает страницу и не показывает формы авторизации;
до проверки сессии они скрыты. Единый контракт имени описан выше в разделе Google и Discord.

В Orchid раздел «Пользователи» (/admin/players): поиск, создание, изменение логина, имени,
  аватара, подтверждённой почты и необязательная смена пароля; удаление с подтверждением.
  Раздел требует отдельного wiki.users и управляет игроками сайта, а не редакторами панели.
  Уникальные контакты не переносятся между аккаунтами, ID/прогресс сохраняются при редактировании.

Ошибки регистрации и восстановления отображаются над соответствующим полем. Поля выделяются
рамкой и фоном, получают aria-invalid и фокус; исправление ввода снимает подсветку.

В формах Orchid игроков браузерный модуль admin-user-validation.mjs проверяет текстовые поля,
адрес аватара и новые пароли до отправки. Он использует общий password-policy.mjs; оба файла
явно включены в API-пакет и загружаются с PHP origin. Сервер независимо валидирует каждый POST,
включая типы вложенных полей, без частичных изменений при ошибке. SQL использует параметры,
HTML имён/поиска экранируется Blade, права wiki.users и CSRF обязательны. Сохраняются CAS,
защита от подмены ID/прав и скрытие хешей/паролей из ответов.

Мобильная верстка кабинета и форм подключается последним файлом `account-responsive.css`
только на странице аккаунта. Гостевые кнопки шапки переносятся, поля имеют размер шрифта
16 px, действия — высоту от 44 px; карточки сводки и кнопки перестраиваются по ширине.
Диалог управления профилем прокручивается и ограничен высотой видимой области.
Проверены экраны 320–844 px, включая альбомную ориентацию, вход, регистрацию с согласиями
и оба шага восстановления. Второй шаг проверяется на локальном макете API без отправки
письма и смены пароля. На сервере проверяется существующий профиль без его редактирования;
состояния входа, скрытие форм и правила проверки пароля остаются прежними.

## Конфликты и смена аккаунта

Действующее автоматическое merge и обязательное поведение при 409/запоздавших ответах
разделены в [контракте клиента/API](client-api-contract.md). Защиту всех запросов поколением
сессии и явный выбор конфликтующей версии нельзя считать внедрёнными без соответствующих тестов.
Аудит административных действий — [отдельный контракт](audit-and-performance.md).
