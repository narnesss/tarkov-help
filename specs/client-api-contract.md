# Совместимость клиента/API, ресурсы и конфликты профиля

Статус на 2026-10-17: обязательные требования и явно отмеченные пробелы реализации.
Деплой Cloudflare не активирует PHP-релиз alwaysdata и наоборот.

## Независимые релизы

Поддерживать старый клиент + новый API и новый клиент + старый API, а не только новую пару.
Для каждого изменения фиксировать минимальные совместимые версии/возможности и окно
поддержки открытых вкладок; оно не может быть короче TTL + stale-while-revalidate старых ресурсов.
Изменение поля: сначала API добавляет совместимый формат, затем клиент переходит на него,
старый формат удаляется только после документированного окна и проверки потребителей.
Клиент должен терпеть неизвестные поля и явно обрабатывать отсутствие новой возможности;
не имитировать успешное сохранение при недоступном API.
Проверять также предыдущие миграции/формат файлов, фоновые запросы и откат кода.

Приёмка релиза: прогнать обе смешанные пары на одном изолированном наборе, включая
401/403/409/422/429/503, вход/выход, старую открытую вкладку и сохранение прогресса.
HTTP /up и зелёная сборка не заменяют эту проверку.

## Автоматическое версионирование браузерных ресурсов

Сейчас в Blade и импортах JS используются ручные query-версии; сборка проверяет свежесть
Blade-экспорта, но это не хеширование полного графа ресурсов.
Требуется отдельная реализация и проверка следующего контракта:
- сборка вычисляет fingerprint CSS/JS и их зависимостей, включая динамические импорты,
  modulepreload, CSS url()/import; меняет адреса entrypoint и зависимых ресурсов;
- manifest и HTML обновляются согласованно; одинаковые байты сохраняют тот же адрес,
  изменённые получают новый. Не полагаться на ручные profile-N и случайное повышение номера;
- HTML/manifest перепроверяются при стандартной перезагрузке, fingerprint-ресурсы можно
  кэшировать надолго. Старые ресурсы сохраняются на всё объявленное окно совместимости;
- HTML активной версии не ссылается на отсутствующие файлы; релиз/откат не ломают
  открытые вкладки. Не допускать смешения старых и новых модулей;
- приёмка: прогреть старый релиз, изменить транзитивный модуль и CSS, опубликовать,
  обычно перезагрузить страницу и проверить реальные URL/байты; затем проверить откат.

Ctrl+F5 допустим как диагностика разработчика, но не как штатная инструкция пользователю.
До внедрения fingerprint нельзя объявлять автоматическую смену всех ресурсов реализованной.

## CAS, локальная правка и 409

Серверный контракт state: value/version; 409 возвращает current. ProfileStore сейчас
сохраняет dirty/base/version и делает до трёх попыток merge; при одинаковом поле
mergeState отдаёт приоритет локальной правке. Явного диалога выбора сторон пока нет.

Требуемое поведение: при 409 сохранить base/local/remote под прежним owner/key;
независимые изменения объединять безопасно, противоречащие поля показать как конфликт.
Предложить выбор серверной/локальной версии, сравнение или экспорт локальной копии;
не перезаписывать ни одну сторону молча. После выбора писать с актуальной version;
повторный конфликт снова обрабатывать ограниченно. При offline/ошибке dirty не теряется,
«сохранено на сервере» показывается только после подтверждения.
Тестировать одинаковое поле, независимые поля, несколько вкладок и новый ввод во время запроса.

## Смена аккаунта и запоздавшие ответы

ProfileStore уже разделяет ключи по owner и проверяет owner перед сохранением успешного
ответа flush; authenticate ожидает flush и сигнализирует другим вкладкам о смене identity.
Это не полная гарантия: у всех запросов и ошибок нет общего поколения сессии.

Требуется generation/epoch, обновляемый при login/logout/OAuth/смене owner:
запрос захватывает owner+epoch; успешный ответ, ошибка, finally, очередь и отложенный callback
меняют UI/storage/CSRF только при совпадении обоих. Старые запросы отменяются по возможности;
одной отмены недостаточно. Старые dirty-данные остаются только в пространстве прежнего владельца,
гостевой прогресс не копируется в именованный аккаунт автоматически.
Приёмка: искусственно задержать GET state, PUT state, ошибку и OAuth ответ, сменить аккаунт,
отпустить ответы в обратном порядке; проверить UI, хранилище, CSRF и отсутствие чужих отметок.

## Существующий статический URL и публикация контента

Worker сейчас использует ASSETS прежде всего и подбирает оболочку для отсутствующего slug.
Полная карточка и данные могут обновляться API, однако это само по себе не обновляет
SEO/статический HTML и не гарантирует снятие старого экспортированного URL с публикации.

Требуется явно реализовать проверку действующего статуса/revision для существующих slug
или актуальную пересборку/инвалидацию HTML, sitemap и навигации. Выбранный механизм должен
обрабатывать edit/unpublish независимо от наличия файла в dist и недоступности origin.
Для снятого квеста выбрать и документировать 404/410; не отдавать старый контент с 200.
При недоступности API не подменять неизвестный статус публикации заведомо устаревшей карточкой.
Приёмка — полный перечень из [контракта данных](data-authority-and-publication.md).
