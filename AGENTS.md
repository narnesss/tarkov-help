# Tarkov Wiki: правила проекта

Единый источник правил — этот файл; `.cursor/rules/*.mdc` ссылаются на него.
Активный план: `specs/002-alwaysdata-api/plan.md`. Требования обязательны в пределах задачи;
рекомендации применяются по необходимости. Правила не дают новых разрешений на деплой,
работу с production, запуск агентов или сообщения в другие чаты.

## Обязательные правила

### Архитектура проекта

- Laravel 13; PHP production/CI — 8.4, минимум — 8.3. Laravel управляет HTTP/DI, Blade, Cache, миграциями и Artisan.
- Исходники страниц — `resources/views/**/*.blade.php`, конфигурация — `config/pages.php`; HTML — экспорт. Blade/public/dist обновлять согласованно.
- Cloudflare Workers публикует dist и не выполняет PHP; Laravel/Orchid/API работает на alwaysdata. Перед изменениями сборки/CI/Wrangler и деплоем читать `specs/cloudflare-deployment.md`; для API/аккаунтов/deploy — `specs/alwaysdata-deployment.md`.
- Production — MySQL-протокол/MariaDB; SQLite — локальная совместимость и сохранённый источник переноса. Старую SQLite после переключения не открывать для записи.
- Изменяемые сущности, связи, аккаунты и прогресс — в БД, обработка — на бэкенде, предоставление — через API, отображение — на фронтенде. Не подменять их статичными файлами или хардкодом.
- Статические CSS/JS/изображения допустимы. Архитектурное исключение: JSON-контент хранится в CONTENT_DIRECTORY вне релиза и обслуживается бэкендом/API; аккаунты и прогресс туда не переносить.
- Сохранять opaque cookie/HMAC CSRF/CAS-контракты src. Worker — same-origin proxy с секретом; forwarded IP доверять только с ним. APP_URL — HTTPS origin Cloudflare; API_ENABLED задаётся панелью, keep_vars сохранять.

### Контракты изменений

- Источники SQL/CONTENT_DIRECTORY/экспорта, точный объём файлового исключения, порядок файл → commit SQL → кэш, crash-проверки/очистка и импорт без потери связей — [контракт данных](specs/data-authority-and-publication.md). Новые семейства данных включать явно.
- Проверять обе смешанные пары старого/нового фронтенда и API; версии ресурсов менять автоматически по зависимостям, 409 разрешать без потери локальной правки, запоздавшие ответы изолировать по owner/epoch — [контракт клиента/API](specs/client-api-contract.md).
- После create/edit/unpublish проверять карточку, поиск/фильтры, карту, связи и SEO, включая URL, уже существующий в dist. Копии/учения должны восстанавливать MariaDB вместе с content; проектные RPO/RTO и внешнее хранение — [контракт восстановления](specs/recovery-contract.md).
- Защищённый аудит Orchid, отдельные права/срок хранения и измеримые бюджеты после исходных замеров — [аудит и производительность](specs/audit-and-performance.md). Документированный целевой механизм не считать реализованным; применять требования при изменении соответствующего участка.

### Границы работы и совместная разработка

- Перед изменениями изучать архитектуру, соглашения, стиль и существующие реализации. Не дублировать функции и не менять несвязанный код; необходимый рефакторинг ограничивать задачей.
- Доводить согласованную функциональность до конца: без заглушек, фиктивных данных, неработающих кнопок и TODO вместо реализации. Незавершённое явно отмечать.
- Сохранять чужие незакоммиченные изменения. Не переключать общий checkout, не делать reset --hard, clean, разрушительное восстановление файлов или force push без явного разрешения; обычная публикация — без force.
- Новые зависимости добавлять после проверки необходимости, поддержки и совместимости; фиксировать версии lock-файлами. Не коммитить vendor, .env, storage и БД.
- Неиспользуемый код, зависимости и файлы удалять только после проверки статических и динамических ссылок и сценариев; отсутствие ссылки в исходниках не доказывает ненужность изображения.
- При изменении API/БД/конфигурации сохранять совместимость потребителей и данных, описывать переход и откат. Соблюдать единый формат ответов/ошибок и пагинацию; отдавать только необходимые разрешённые поля.
- Коммиты, документация и новые PHPDoc — по-русски. Обновлять инструкции запуска, настройки и API вместе с кодом; архитектуру — в `docs/architecture/class-map.md` и `docs/architecture/database-map.md`.

### Безопасность и данные

- Авторизацию и права проверять на бэкенде для каждой защищённой операции. Проверять CSRF и версию записи; разрешать только предусмотренные поля, не допускать mass assignment чужих ID и связей.
- Валидация фронтенда — для удобства; независимая валидация бэкенда обязательна. Проверять структуру, типы, обязательность, длину, диапазоны, конечность чисел, допустимые значения и связи; bail — до unique/exists. Массив вместо строки должен давать 422, а не 500.
- Обычный текст и поиск нормализовать через AdminInput::trim/search, сохраняя внутренние переносы. Пароли, токены, HMAC/CSRF, подписи, зашифрованный _state, стабильные ID и JSON pointers автоматически не обрезать; глобальный trim для API не включать.
- Обычный текст админки — через AdminInput::rules; URL — HTTP(S) или безопасные относительные пути. HTML/управляющие символы не принимать там, где требуется обычный текст.
- SQL — только Eloquent/Query Builder/bindings; имена колонок, таблиц и сортировку выбирать из серверного белого списка. trim() и удаление HTML не защищают от SQL-инъекций.
- Хранить текст без HTML-экранирования; выводить через Blade {{ }}/e() или DOM textContent. Для HTML/JS/CSS/URL применять защиту соответствующего контекста; не вставлять пользовательский текст в {!! !!}/innerHTML. Кавычки и HTML-подобный поиск допустимы как буквальный текст.
- Загрузки проверять на сервере по размеру, фактическому типу и разрешённому формату; не доверять расширению/MIME клиента. Исключать выполнение содержимого, обход путей и перезапись чужих файлов; активные форматы разрешать только с безопасной обработкой.
- Связанные записи защищать FK/unique и другими нужными ограничениями, транзакциями, идемпотентностью и CAS; повторные запросы и параллельное редактирование не должны терять или дублировать данные.
- Схему менять миграциями с повторным запуском и планом отката. Сохранять .env/APP_KEY, ID, связи, аккаунты и прогресс; перед изменением production-данных делать согласованный SQL backup. Перед потенциально разрушительной миграцией проверять восстановление копии в отдельном окружении; необратимость документировать.
- Окружения разделять, настройки выносить в конфигурацию, примеры env поддерживать без секретов. Секреты не помещать в Git, HTML, фронтенд и публичные сборки.
- Логировать ошибки с полезным техническим контекстом, без паролей, токенов и персональных данных. Пользователю не раскрывать внутренние ошибки, SQL, файловые пути и стек вызовов.
- Явно задавать часовые пояса и единицы измерения; временные метки хранить в UTC и преобразовывать для отображения, календарные даты не сдвигать как timestamps. Деньги считать в минимальных целых единицах или DECIMAL, не через float.

### Ресурсы и внешние сервисы

- Ограничивать длительность внешних запросов, размер ответа/выборки, число попыток и время повторов. При сбое API давать понятную ошибку и ограниченную безопасную повторную попытку; не допускать бесконечного ожидания и повторов.
- Длительные пользовательские задачи выполнять через очередь с поддерживаемым обработчиком, лимитами и защитой от повторной обработки. Тяжёлые импорты/миграции — ограниченными возобновляемыми пакетами; не держать несколько полных каталогов в памяти и не переиндексировать всё ради нескольких записей.
- Определять TTL, ключи и инвалидацию кэша; после изменения через админку сайт должен обновляться без ручной очистки. Общий кэш — только публичный; API/личный прогресс — private, no-store. Origin fetch — cache: 'no-store'; cf.cacheTtl=0 не использовать.
- Изображения сжимать и подбирать размеры до загрузки/публикации, применять WebP/AVIF при поддержке; сохранять читаемость, прозрачность, необходимые оригиналы. Не загружать неоправданно большие файлы и не делать lazy loading основного изображения первого экрана.

### Интерфейс и SEO

- Любое изменение UI сайта и Orchid сразу делать для телефона, планшета и десктопа. Проверять реальные страницы в браузере при ширинах 320/390, 768/1024, 1280/1440 CSS px, границы затронутых breakpoint и поворот планшета/изменение размера открытого окна. Эмуляцию не выдавать за физическое устройство.
- Проверять длинные подписи, переполнение, прокрутку, меню, селекты, фильтры, таблицы, формы и диалоги. Окна/фиксированные панели не должны перекрывать поля и действия; горизонтальная прокрутка допустима внутри ограниченного контейнера таблицы/карты, не всей страницы.
- Клавиатура, видимый фокус, подписи полей, контрастность и сенсорное управление обязательны; основные сенсорные цели — не меньше 44×44 CSS px, действия не зависят только от hover.
- Предусматривать загрузку, пустое состояние, ошибку и безопасную повторную попытку; взаимоисключающие блоки не показывать вместе. Ошибки — рядом с полем, безопасным текстом, с is-invalid, aria-invalid и aria-describedby; клиентские ограничения согласовать с серверными.
- При ошибке отправки сохранять обычный пользовательский ввод; не сохранять пароли/токены в постоянное хранилище. Предупреждать о потере несохранённых изменений, удаление сопровождать подтверждением или возможностью отмены.
- SEO публичных страниц: корректные статусы/индексация, уникальные title/description, canonical, семантика и уместная структурированная разметка, понятные URL, актуальные sitemap.xml/robots.txt, скорость и адаптивность. Значимый контент/метаданные должны быть в HTML робота (серверный рендеринг/актуальный экспорт), не только после JS. Личные страницы и админку не индексировать; robots.txt не является защитой доступа.

### Коммиты, публикация и передача работы

- Один коммит — одно самостоятельное проверяемое изменение; не смешивать несвязанные UI/БД/авторизацию/контент. Массовые изображения/контент делить по квесту, локации или типу. При объёме свыше 20 ручных файлов или 300 содержательных строк пересмотреть разбиение, не ломая зависимости.
- Исходники, необходимые ассеты, тесты и согласованный экспорт держать вместе. Много генерируемых файлов допустимо; дробление коммитов не уменьшает само по себе полный релиз или расход памяти.
- При разрешённом деплое отправлять в main один проверенный этап; несколько коммитов одним push — один деплой. Дождаться CI, Cloudflare и alwaysdata конкретного SHA, проверить изменённый сценарий на сервере и только затем выпускать следующий этап. При сбое остановить последующие публикации и устранить причину.
- Работать от свежего main, не переносить устаревшие сборки поверх новых правок. Самостоятельный параллельный деплой из бокового чата — только по явному поручению.
- Боковой чат фиксирует репозиторий, абсолютный путь копии, ветку/detached HEAD, SHA, готовность, изменённые/новые незакоммиченные файлы, проверки, зависимости и остаток работы. Передачу сохранять в `build/side-chat-handoffs/<тема>.json` основного checkout и повторять в ответе; не включать секреты/БД/личные данные. Если разрешён Git, готовить небольшие коммиты.
- Основной чат перед следующей задачей сверяет готовые правки известных боковых копий/веток, свежий main, статусы, `build/side-chat-handoffs/*.json` и прежние `build/*-ready.md`; сначала интегрирует готовое. Незавершённое сохранять, блокеры указывать; при отсутствии правок сразу продолжать задачу.
- При поручении собрать боковые чаты составить полный перечень задач и сопоставить с копиями/файлами/коммитами и статусами. Учитывать копии без Git и незакоммиченное; не судить о полноте по числу веток, об эквивалентности — только по SHA. Недостающие темы уточнять, отчёт давать по каждой задаче.

## Обязательные проверки и критерии готовности

- Новую/изменяемую функциональность покрывать необходимыми тестами поведения, ошибок и регрессий. Проверять пустое значение, ноль, длинный текст, спецсимволы, большие объёмы и частичные записи.
- Тесты изолировать от production-данных и реквизитов. Время фиксировать/внедрять, случайность контролировать, внешние сервисы заменять управляемыми ответами; отдельные интеграционные проверки помечать и ограничивать тайм-аутами.
- Критический путь проверять целиком: интерфейс → запрос → запись в БД → результат после перезагрузки; для аккаунтов/прогресса сверять ID и связи. Для форм — неверные типы, буквальные SQL/XSS/опасные URL, права/CSRF/CAS и отсутствие частичной записи при отказе на изолированных SQLite/MariaDB.
- Не отключать тесты, линтеры и защиту ради успеха; не подавлять ошибки вместо исправления. Ожидания тестов менять только при обоснованном изменении поведения, сохраняя проверяемую регрессию.
- Только документация/правила: проверить точность команд, ссылок и непротиворечивость, выполнить `git diff --check`; полную сборку без отдельной причины не запускать.
- Разработка: `php -l` для изменённых PHP и `node --check` для JS/MJS; профильные тесты, например `php artisan test --filter=ContentUpdatesTest` или `node --test tests/cloudflare/quest-media-localization.test.mjs`. Отдельного `npm run lint` в проекте нет.
- Код/Blade/ресурсы/контент перед публикацией — полный набор по порядку:

```sh
composer install --no-interaction --prefer-dist
php artisan site:export
npm run build
npm test
php artisan test
php tests/php/run.php
node scripts/check-export-freshness.mjs
npx --yes wrangler@4.151.0 deploy --dry-run
git diff --check
```

- После фиксации экспорта `git diff --exit-code -- public dist` должен быть чистым; проверка свежести обязана отклонять устаревший экспорт.
- БД/ORM/импорт/связи/аккаунты/прогресс: дополнительно `php vendor/bin/phpunit -c phpunit.mysql.xml` на тестовой MariaDB. Перенос/backup/restore: `php scripts/check-mysql-migration.php`; реквизиты только тестовые, через окружение, как в job mysql `.github/workflows/check.yml`.
- Упаковка/деплой/восстановление: дополнительно `npm run package:alwaysdata`, `php scripts/check-alwaysdata-deployment.php`, `php deployment/alwaysdata/check-restore.php` в изолированном окружении; API_ONLY и состав архива — по CI и `specs/alwaysdata-deployment.md`.
- UI: проверить затронутые состояния/действия на всех трёх форматах; карты — уровни, управление и точки; общая раскладка/навигация — обход затронутых разделов. SEO — исходный HTML; кэш — повторная загрузка и обновление после записи.
- Проверки на сервере — только с разрешёнными тестовыми данными и их последующей очисткой; реальные аккаунты/контент/прогресс ради теста не менять.
- Готовность: реализация завершена, проверки пройдены, данные/совместимость сохранены, документация актуальна, diff ограничен задачей. Отчёт: что изменено, фактически выполненные проверки и результаты, ограничения и непроведённые проверки с причинами. Не считать коммит публикацией, зелёный pipeline — проверкой всей функции, непроведённую проверку — успешной.

## Рекомендации по применению

- Выбирать простейшее достаточное решение; паттерны применять для конкретной проблемы. Оптимизировать по измерениям, устранять подтверждённые N+1, лишние запросы/вычисления; индексы и кэш добавлять по реальной нагрузке.
- Для адаптивности предпочитать гибкие сетки, minmax/min-width: 0, переносы, ограничение медиа, подходящие srcset/sizes и lazy loading вне первого экрана; содержимое не прятать ради устранения переполнения.
- Планировать поисковое продвижение с оценкой эффекта: сравнивать исходные и последующие индексацию, показы, клики, CTR, позиции и органический трафик по доступным разрешённым источникам.
